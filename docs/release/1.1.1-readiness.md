### 5.1 `testDebugUnitTest`（Gradle 方式）——联接方案无效、`subst` 方案验证通过

本轮按任务包指示建立了 `D:\AIProjects\cache\lf-ascii` 目录联接（`New-Item -ItemType Junction`，
等价 `mklink /J`）指向本仓，并通过联接路径运行 `testDebugUnitTest`。**结果：仍然失败**，但失败点比
1.1.0 轮更深一层：

- 1.1.0 轮：Gradle 测试 worker 进程**自身启动失败**（`ClassNotFoundException: GradleWorkerMain`）。
- 本轮（通过联接）：worker **成功启动**，只是加载不到具体的测试类（`ClassNotFoundException:
  io.github.linkwutcreate.localfind.server.DiscoveryEndpointPolicyTest` /
  `...onboarding.VendorGuideTest`）。

**根因实锤**：检查 Gradle 写出的 worker classpath 临时文件（`D:\AIProjects\cache\lf-gradle\.tmp\
gradle-worker-classpath*.txt`）发现，其中的路径**被解析回了原始中文路径**
（`D:\AIProjects\projects\local-find（找手机app）\android\...`），而不是联接路径
（`D:\AIProjects\cache\lf-ascii\android\...`）。这是 Windows/Java 的既定行为：NTFS 目录联接是文件系统
重解析点，Java 对项目目录做 `getCanonicalPath()` 时会把联接**规范化解析回真实目标路径**——这正是
联接机制的设计本意，否则联接就不透明了。因此"建联接绕开中文路径"这个思路，在 Gradle/Java 的路径规范化
面前天然失效，**不是配置没调对，是这个技术方案本身对这一层问题无效**。

翻查 2026-09-14 的构建日志（`android/build-debug-subst-20260914.log`）发现，**`subst` 盘符映射方案
当时实测能跑通到 `assembleDebug`**（只在写一个无关的诊断报告文件时报权限错误，非编码问题）——
`subst` 是驱动器号级别的 DOS 设备映射，不会被同样的路径规范化机制穿透。本会话原地复验 `subst` 时
一度被 Claude Code 的 auto 模式安全分类器以「Unauthorized Persistence」拦截（任务包只白名单了
`mklink /J` 联接，未提及 `subst`），已写入 `_dispatch/questions/LOCALFIND-RC2-0924.md` 请求用户裁决。

**代码正确性的独立证明**（绕开 Gradle 测试 worker）：直接用同一份编译产物 + 依赖 jar 通过原生
`java -cp ... org.junit.runner.JUnitCore <TestClass>...` 运行两个测试类，**25 个测试全部通过**，
证明失败完全在 Gradle 自身机制，与被测代码或测试代码的正确性无关。

**裁决后（同日晚）**：用户明确授权试验 `subst`（说明了其临时、可撤销、仅对本仓路径生效的性质后，
用户回复同意）。手动 `subst X:` 后 `gradlew --no-daemon testDebugUnitTest` → `BUILD SUCCESSFUL
in 41s`，JUnit XML 报告核实 `tests=9 failures=0`（DiscoveryEndpointPolicyTest）、
`tests=16 failures=0`（VendorGuideTest）——**这才是 Gradle 真实跑通的结果**，不是绕开 worker 的
独立证明。随后把 `tools/build-android.ps1` 固化为 subst 版本（`-DriveLetter` 取代
`-JunctionPath`），并在续做会话里用脚本本身（非手动操作）以 `--rerun-tasks` 强制重跑复核：
`BUILD SUCCESSFUL in 37s`，23/23 任务全部执行（非缓存命中），JUnit XML 报告数字与上面一致
（时间戳 2026-09-24T13:53:03）。跑完立即撤销 subst 映射（`subst X: /D`，确认无残留），脚本改动
提交 `e563872`。
