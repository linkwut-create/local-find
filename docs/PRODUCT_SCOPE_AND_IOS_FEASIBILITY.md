# 产品定位与跨平台可行性分析

**日期**: 2026-09-10
**状态**: 定位纠正 + 可行性结论

---

## 0. 产品定位（唯一权威）

> **Local Find 只找手机，不找电脑。**

- **被寻找端（target）**：**只能是手机**（Android，未来可能含 iPhone）；
- **控制端（controller）**：可以是手机，也可以是电脑上的浏览器扩展。

"电脑上的浏览器扩展"是**控制端**，不是被寻找端。因此
**"让电脑被找到"从来不在产品范围内**——电脑只是发起寻找的工具。

> ⚠️ 本文档纠正 2026-09-10 早前一次口头建议中提出的"Mac 守护进程作为被寻找端"方案。
> **该方案因违反产品定位而作废，不再推进。**

---

## 1. 为什么 iOS 是真正的难题

现有架构里有一个关键的角色分配：

```
被寻找端(手机) = 服务端   →   Ktor HTTP 服务器 + NSD/mDNS 广播 + 前台服务
控制端(手机/电脑) = 客户端 →   HTTP 请求 + mDNS 浏览
```

**这个角色分配与"被寻找端必须常驻监听"是绑定的。** 而 iOS 恰好不允许这件事：

| iOS 限制 | 后果 |
|---|---|
| 无 Android `foregroundService` 等价物 | App 进入后台即被挂起 |
| 挂起后监听 socket 被回收 | **锁屏时收不到任何请求** |
| 后台无法访问相机 | 无法后台点亮闪光灯 |
| 系统提示音/震动受后台策略限制 | 无法可靠响铃 |
| Find My 网络为 Apple 私有蓝牙广播 | 第三方**无法接入**，这条路封死 |

而"找手机"的使用时刻，**恰恰就是手机被锁屏/不在手上的时刻**——也就是 iOS 一定会挂起的时刻。
这不是工作量问题，而是平台级的正面冲突。

## 2. 可行性结论

| 场景 | 结论 | 说明 |
|---|---|---|
| **Android ↔ Android 互找** | ✅ 可行 | 当前已实现并验证 |
| **电脑浏览器 → 找 Android 手机** | ✅ 可行 | 扩展为纯 MV3，跨操作系统一致，**无需另做开发** |
| **手机浏览器 → 找 Android 手机** | ✅ 可行 | 同一套 HTTP 协议 |
| **iPhone 作为控制端** → 找 Android 手机 | ⚠️ 有限可行 | 仅前台可用，可做，但价值有限 |
| **iPhone 作为被寻找端**（锁屏找 iPhone） | ❌ 不可行 | 后台挂起，无持久监听；平台级限制 |
| **Android ↔ iPhone 互找** | ❌ 不可行 | 两端需同时在线监听，iPhone 做不到 |
| **iPhone ↔ iPhone 互找** | ❌ 不可行 | 两台都可能同时被挂起 |

### 2.1 如果坚持做 iOS，只有这一条路

只能做**控制端**（用 iPhone 去发指令找 Android 手机 / 找别的设备），
且必须接受"**仅前台可用**"的限制——切到后台即失去发现与连接能力。

这与"找丢失的手机"这个核心场景**几乎无关**：丢手机的人需要的是**被寻找端**常驻。

### 2.2 由此得出的建议

**不建议把 iPhone 作为被寻找端**。如果要做 iOS，定位应是
"iPhone 作为遥控器"，并且必须在产品说明里明确写出"iOS 版无法被寻找"，
否则会造成用户预期与现实的严重不符。

## 3. 桌面/非 Windows 平台的技术结论

**结论：不需要为 macOS / Linux 做任何新开发。**

依据（已核对 `chrome-extension/manifest.json` 与 `popup.js`）：

| 事实 | 影响 |
|---|---|
| 扩展是纯 Manifest V3 | 无平台绑定 |
| 权限仅 `storage` + `http://*/*` | 无原生依赖 |
| **无 `nativeMessaging`** | 不需要安装任何本地宿主程序 |
| 无 `chrome.system` / `chrome.os` | 无操作系统特定 API |

因此在 macOS、Linux、ChromeOS、Windows 上行为**完全一致**，直接安装即可用于
"在电脑上找 Android 手机"。

### 3.1 唯一的体验限制（非平台问题）

扩展目前**不做 mDNS 发现**，靠手动输入 IP + 端口 `8888` 连接；
Android 端界面会显示本机 IP 和二维码。

这个限制在**所有操作系统上都一样**，不是 macOS 特有的。若要实现"零配置发现"，
需要给浏览器补一个 mDNS 通道（原生宿主或本机小助手），属于**可选优化**，
与"是否支持 Mac"无关。

## 4. 对文档的影响

- 本文档作废此前"Mac/Linux 守护进程作为被寻找端"的建议；
- `PLAY_UPLOAD_RUNBOOK.md` 及 Android 相关文档不受影响；
- 后续如推进 iOS，需新建独立规划书，并明确"仅控制端 + 前台限制"。
