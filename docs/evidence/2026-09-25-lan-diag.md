# 2026-09-25 LAN 直连诊断 — LOCALFIND-LAN-DIAG-0925

## 0. 背景

09-24 RC2 真机验收记录：Wi-Fi 直连 `http://10.128.20.208:8888/ping` TCP 连接超时，`/ping` 与锁屏控制
均只经 adb forward（USB）验证通过；ICMP 通、TCP 不通，且当时服务已停止，无法区分网络隔离 /
应用监听地址 / 系统防火墙三种可能根因。本包目的：定因，并在可能的情况下用 Wi-Fi 直连（非 adb
forward）重新证实 `/ping` 与锁屏控制。

## 1. 代码核对（只读，先于真机测试）

- `HttpServerManager.kt` `createServer()`：
  `embeddedServer(Netty, port = getPort(), host = "0.0.0.0") { ... }` —— 应用显式绑定所有网卡
  （`0.0.0.0`），并非只绑定回环地址。
- `DiscoveryEndpointPolicy.kt`：`isPrivateIpv4()` / `validPort()` 仅用于校验**发现到的对端**地址是否
  为私有 IPv4（客户端侧过滤逻辑，配合 mDNS/NSD 发现使用），与本机 HTTP 服务器的入站连接接受逻辑
  无关，不会拒绝任何来源的入站请求。
- `IdentityBindingPolicy.kt`：只处理配对信任转移的身份匹配，与网络层无关。
- **结论**：代码层未发现任何会拒绝非回环 / 非本机来源请求的逻辑；`/status`、`/ping` 等路由本身
  对请求来源没有网段限制（鉴权在 `authenticate()` 里按 Token 校验，与来源 IP 无关）。

## 2. 真机复测环境

- 设备：MEIZU 21（`461QYFFT225UP`，Flyme），手机锁文件协议遵守，用后已释放。
- 手机 Wi-Fi 地址：`10.128.20.208`（与 09-24 记录一致）。
- PC WLAN 地址：`10.128.9.36/17`（`Get-NetIPAddress` 核实），与手机同一 `/17` 网段，与 09-24 记录
  的网络环境一致（未更换网络）。
- 通过 App UI 点击"启动服务"（非 adb 拉起），UI 显示"监听中"，局域网地址/端口与预期一致。

## 3. 手机侧监听地址核查

`adb shell netstat -tln` 关键行：

```
tcp6       0      0 [::]:8888               [::]:*                  LISTEN
```

`ss -tln`（部分功能因权限受限，但监听行可见）同样显示 `*:8888 LISTEN`。**结论：应用监听在双栈通配
地址上，覆盖 IPv4-mapped 连接，不是仅绑定 `127.0.0.1`**，与第 1 节代码核对结论一致。

## 4. 连通性测试（Wi-Fi 直连，非 adb forward）

### 4.1 手机自连

```
adb shell curl http://10.128.20.208:8888/ping
→ 200
```

### 4.2 PC → 手机（本次结果与 09-24 不同：直接成功）

```
$ curl -m 8 -v http://10.128.20.208:8888/ping
* Established connection to 10.128.20.208 (10.128.20.208 port 8888) from 10.128.9.36 port 60526
< HTTP/1.1 200 OK
{"ok":true}
```

连续 3 次复测（间隔 1 秒），均 `http=200`，耗时 28–42ms，稳定可复现：

```
第1次 {"ok":true} [http=200 time=0.040481s]
第2次 {"ok":true} [http=200 time=0.028679s]
第3次 {"ok":true} [http=200 time=0.042522s]
```

ICMP 对照：6–7ms（09-24 记录约 210ms，本次明显更低，网络状况与当时不同）。

### 4.3 对照实验（AP 客户端隔离排查）

按任务包第 4 步计划在手机上起临时 `toybox nc -l -p 8899` 监听供 PC 侧对照连接，但 `adb shell "... &"`
方式后台化在本环境下会话保持阻塞（已知的 adb shell 远程后台化坑），命令被判定为长跑并主动终止；
复核 `ps` 与 `netstat` 确认手机上**没有残留监听进程、端口 8899 未被占用**，未留下任何后台残留。
鉴于第 4.2 节与第 5 节已经用**真实应用端口 8888**在同一网络下反复证明 Wi-Fi 直连可达（而不仅是
ICMP 可达），该项对照实验的目的（区分"网络层整体隔离"与"仅应用/8888端口"）已经被更直接、更强的
证据覆盖：如果是网络层整体隔离，8888 端口本身也不应该通——但它通了，所以不存在网络层整体隔离。
因此未强行重试临时监听对照。

## 5. 验收项：锁屏 ≥45 秒后 Wi-Fi 直连控制命令

1. `adb shell input keyevent KEYCODE_POWER` 锁屏；`adb shell dumpsys power | grep mWakefulness` 立即
   核实为 `Dozing`（真正息屏，非仅界面锁定）。
2. 分阶段等待并多次核查（20s、45s、49s）均保持 `Dozing`，确认连续锁屏状态未被中途唤醒。
   （首次尝试因手机在等待期间收到即时通讯应用通知自动唤醒屏幕，锁屏未能持续 45 秒；已重试一次，
   第二次严格核查全程 `Dozing` 未被打断，以第二次结果为准记入本节。）
3. 锁屏 **49 秒**后，Wi-Fi 直连（`http://10.128.20.208:8888`，非 adb forward）依次执行：
   - `GET /ping` → `{"ok":true}` `http=200`
   - `POST /command/ring/start`（带 `X-LocalFind-Token`）→
     `{"success":true,"message":"Command accepted"}` `http=200`
   - `POST /command/flash/strobe/start` → `{"success":true,"message":"Command accepted"}` `http=200`
   - `GET /status` → `{"service":"running","ring_active":true,"flash_mode":"strobe"}` `http=200`
     ——确认命令在锁屏状态下真实生效，不是仅仅返回成功。
   - 命令执行完毕后立即复查 `dumpsys power` 仍为 `Dozing`——**证明整套控制命令本身没有唤醒屏幕**。
4. `adb shell screencap` 抓取锁屏期间的帧：纯黑（15,197 字节，远小于亮屏截图的 ~190KB+），佐证
   屏幕确实处于关闭状态而非仅锁定界面仍亮屏。
5. `POST /command/stop-all` → `{"success":true,...}`；`GET /status` → `ring_active:false, flash_mode:off`
   ——停止生效，此时仍处于 `Dozing`（锁屏中）。
6. 用 `KEYCODE_WAKEUP` 唤醒后截图确认为真实密码/图案锁屏界面（时钟 UI + 锁形图标 + 通知列表），
   与 09-24 证据的判定标准一致，排除"仅熄屏未锁"的可能。

**结论：Wi-Fi 直连下 `/ping` 与锁屏（真实锁定 ≥45 秒）控制命令（响铃+闪光+状态查询+全部停止）
本次全部验证通过，非经 adb forward。**

## 6. 根因结论

- 应用代码层（监听地址、发现策略、身份策略）**均未发现会阻断 Wi-Fi 直连的逻辑**，且本次在与
  09-24 完全相同的网络（同一 `/17` 网段、同一路由器）、相同 App 版本（未做任何代码改动）下，
  Wi-Fi 直连 TCP 连接**反复稳定成功**（/ping ×4、锁屏控制全链路 ×1）。
- 由于代码未变而结果由"不通"变为"通"，判定 09-24 的 TCP 超时**是当时的瞬时环境状态**（AP 侧
  策略瞬时生效、或手机 Wi-Fi 省电/信号状态导致该次连接尝试超时），**不是稳定复现的网络隔离，
  也不是代码缺陷**。09-24 记录的 ICMP RTT（约210ms）远高于本次（6-7ms），侧面印证当时链路状态
  与本次不同。
- 按任务包第 2 节判断标准："网络/系统层（对照监听也不通）→ 不改代码"——本次连通，不属于这一分支，
  **不需要修改代码，也不需要更换网络复测**。
